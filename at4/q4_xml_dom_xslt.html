Question 4. A city events portal receives event details from several organisers as an XML feed (event name, venue, date, fee and category). Design a PHP solution that reads, modifies and presents this feed. Explain the XML DOM tree and its node types; the use of DOMDocument and DOMXPath (and SimpleXML) to traverse the tree, select nodes with XPath, add a new event, update a fee and delete a cancelled event; and the comparison of DOM with SAX or pull parsers for large files. Then write an XSLT style sheet that converts the feed into an HTML table showing only events of one category, sorted by date, and explain the elements xsl:template, xsl:for-each, xsl:value-of, xsl:sort, xsl:if or xsl:choose and xsl:param. Show how PHP applies the style sheet with XSLTProcessor, and justify server-side versus client-side transformation in terms of performance, compatibility and security.
Marks (10)   (CO4)   (BL5)

ANSWER 4 – Events feed: reading, modifying and presenting XML with PHP and XSLT

Solution. The portal keeps the organisers' feed as events.xml. PHP loads it with DOM, uses XPath to find nodes, adds, updates and deletes events, and then presents it by applying an XSLT style sheet on the server. Large feeds are read with a streaming (pull) parser.

A. The XML DOM tree and node types

The Document Object Model represents a document as a tree of nodes. The events element is the root; each event is a child element; name, venue, date and fee are its children, and their text is stored in text nodes.

Whitespace between tags also becomes text nodes unless preserveWhiteSpace = false is set, which is why the code sets it before loading.

B. DOMDocument, DOMXPath and SimpleXML

  • DOMDocument loads, creates, changes and saves the tree (load, createElement, appendChild, removeChild, save).
  • DOMXPath selects nodes with path expressions and can calculate (count(), sum()).
  • SimpleXML offers shorter object-style access ($xml->event[0]->name, $xml->xpath(...)), good for quick reading; DOM is better for detailed editing.
XPath expressionMeaning
//event[@category='Music']All events whose category attribute is Music
//event[@id='E101']/feeFee element of one event
//event[@status='cancelled']Cancelled events (to delete)
//event[fee > 400]Events with fee above 400
count(//event) / sum(//event/fee)Number of events / total of fees

A copy of the node list is taken (iterator_to_array) before deleting, because removing nodes while looping over a live DOMNodeList skips items. createTextNode() is used for new values so that characters such as & are escaped correctly (Rock &amp; Roll).

PHP offers SAX-style callbacks (xml_parser_create()) and the pull parser XMLReader; XMLReader is the usual choice. For a feed with millions of events the portal should stream with XMLReader, convert one event at a time with expand(), and keep memory constant. Because the portal's own feeds are small, DOM is used for editing.

E. Applying the style sheet in PHP with XSLTProcessor

The category parameter is checked against a whitelist before it is passed to the style sheet, LIBXML_NONET stops the parser from fetching network resources, and registerPHPFunctions() is not enabled, so a style sheet cannot execute PHP code.

F. Server-side versus client-side transformation

CriterionServer-side (PHP XSLTProcessor)Client-side (browser XSLT)
PerformanceUses server CPU, but the result can be cached; browser receives small ready HTML; works on weak phonesServer sends raw XML plus style sheet (more data); each user's device does the work; no server cache of the HTML
CompatibilitySame output for every browser, crawler and app; no browser support neededDepends on the browser; browsers support only XSLT 1.0, and Chrome's published plan was to stop XSLT working in stable releases from Chrome 158 (17 Nov 2026), with Firefox and WebKit also indicating removal plans. Verify the current status before relying on it
SecuritySource XML and rules stay on the server; input can be validated and the processor locked down; but the server must be protected against XXE and untrusted style sheetsRaw feed and style sheet are exposed to users; the browser XSLT engine (libxslt) is a large attack surface, which is the reason browser vendors give for removing it
OtherSearch engines can read the HTML; easy to log and testOffloads work from the server only for very high traffic, and SEO suffers

Justification. The portal should transform on the server: the HTML can be cached, every browser and search engine receives the same result, the whole feed and the processing rules stay under the portal's control, and it avoids dependence on browser features that are being removed. Client-side XSLT would only be considered for an internal tool where the browser is fixed and traffic is very high.
