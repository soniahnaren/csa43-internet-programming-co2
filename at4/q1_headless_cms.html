Question 1. An educational institution wants to publish news, events and course notices through a headless CMS built with PHP, so that the same content can be delivered to its website, mobile app and notice-board screens. Staff submit content through an admin form (title, author e-mail, publish date, category, summary and a staff ID in the format of two capital letters followed by four digits), and the CMS stores it in a MySQL database and exposes it as JSON and XML through an API. Develop the PHP solution by explaining the use of variables and data types, program control structures, and built-in functions (for example, trim, strlen, str_replace, date, json_encode, array functions); form validation and sanitisation (empty checks, filter_var, htmlspecialchars) with regular expressions (preg_match) for the e-mail and staff ID; and connecting to the database with PDO and prepared statements. Differentiate a headless CMS from a traditional coupled CMS, and evaluate the security and performance issues of the design.
Marks (10)   (CO4)   (BL5)

ANSWER 1 – Headless CMS with PHP, PDO and MySQL

Solution overview. Staff enter content in an admin form. PHP validates and sanitises it, stores it in MySQL through PDO prepared statements, and a read-only API publishes it as JSON or XML. The website, mobile app and notice-board screens are separate front ends that only consume the API.

A. Variables and data types

A PHP variable starts with $ and needs no declaration. Its type is decided by the value it holds (dynamic typing), and a value can be converted automatically (type juggling). Form data always arrives as strings, so numbers must be cast explicitly, for example (int)$_GET['page']. declare(strict_types=1); stops function arguments from being silently converted. Constants are defined with const, and $_POST, $_GET, $_SERVER and $_SESSION are superglobals available everywhere.

B. Program control structures

  • Selection – if / elseif / else applies each validation rule; match or switch picks an option; $a ?? $b and ? : give short defaults.
  • Iteration – foreach loops over the form fields and over database rows; while ($row = $stmt->fetch()) can stream large results.
  • Jump / exit – return, exit and continue stop processing early (for example HTTP 405 for a wrong method).
  • Exception handling – try { ... } catch (PDOException $e) { ... } keeps database errors away from the user.

D. Form validation and sanitisation

Validation decides whether a value is acceptable; sanitisation cleans a value; escaping makes a value safe for the place where it is printed. All checks run on the server, because HTML5 attributes (required, type="email") only help honest users. A correct design uses three layers: validate on input, use prepared statements for SQL, and escape with htmlspecialchars() on output.

Staff ID pattern /^[A-Z]{2}[0-9]{4}\z/: ^ anchors the start, [A-Z]{2} means exactly two capital letters, [0-9]{4} exactly four digits and \z the absolute end of the string ($ would still accept a trailing newline). It accepts AB1234 and rejects ab1234, ABC123, AB12345 and AB 1234.

E. Connecting to MySQL with PDO and prepared statements

PDO is a database-independent interface. The DSN names the driver, host, database and character set. Three options matter: ERRMODE_EXCEPTION (errors are thrown, not hidden), FETCH_ASSOC (rows as arrays) and EMULATE_PREPARES => false (the server prepares the statement). With a prepared statement the SQL text is sent first with placeholders (:title) and the values are sent separately, so the input is never treated as SQL. A value such as '; DROP TABLE content; -- is stored as harmless text. The application should connect with a least-privilege MySQL account (SELECT and INSERT only), with credentials read from environment variables.

F. Exposing the content as JSON and XML

api/content.php accepts only GET, validates format, category, page and limit, runs a prepared SELECT with LIMIT/OFFSET bound as integers, and returns either format from the same data. JSON uses json_encode; XML is built with DOMDocument and createTextNode, which escapes &, < and >. The public output leaves out the author e-mail address.

Verdict. For an institution that must serve one set of notices to a website, a mobile app and several screens, the headless design is justified: content is entered once, each channel is free to display it in its own way, and the public surface is a small read-only API that is easy to cache and protect. Its costs are extra components and the loss of built-in preview and SEO rendering. These are acceptable if the controls above are applied (prepared statements, output escaping, CSRF tokens, hashed passwords with HTTPS, a least-privilege database user, caching and pagination). If the institution had only a single website and no developers, a coupled CMS would be simpler.
