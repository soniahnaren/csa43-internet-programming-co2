Question 3. An online electronics retailer exchanges its product catalogue with suppliers as XML files containing product ID, name, category, price, stock quantity and warranty period. Analyse how the catalogue can be controlled using XML Schema (XSD): write an XSD that defines a root element, simple and complex types, attributes, an enumeration for category, a pattern for the product ID, and range restrictions (minInclusive and maxInclusive) for price and stock. Differentiate well-formed from valid XML and compare DTD with XML Schema. Explain how XML parsers (non-validating and validating; DOM and SAX) check a document and how validation is performed in PHP (for example, DOMDocument with schemaValidate), and examine three kinds of errors that a validating parser would report for a faulty supplier file, with the way each error is corrected.

ANSWER 3 – Controlling the product catalogue with XML Schema (XSD)

Idea. The supplier files are exchanged between organisations, so the retailer needs a contract that every file must satisfy before it is imported. An XSD describes the allowed elements, order, attributes and value ranges, so mistakes such as a wrong product ID, an unknown category or a negative price are rejected automatically.

A. Sample supplier file (valid)

B. The XSD

RequirementHow the XSD meets it
Root element<xs:element name="catalogue"> with a required supplier attribute
Simple typesproductIdType, categoryType, priceType, stockType, warrantyMonthsType are restrictions of built-in types
Complex typesproductType (sequence of five child elements plus an attribute); priceElementType and warrantyElementType (text content with an attribute, using simpleContent)
Attributesid (required) on product, currency (default INR) on price, unit (fixed "months") on warranty, supplier on catalogue
Enumerationcategory must be Mobile, Laptop, Audio, Television or Accessory
PatternProduct ID P[0-9]{5} (letter P and five digits)
Range restrictionsPrice: minInclusive 1.00, maxInclusive 500000.00, 2 decimals. Stock: 0 to 10000. Warranty: 0 to 60 months
Structure rulesxs:sequence fixes the order; minOccurs/maxOccurs allow one or more products; xs:unique rejects duplicate IDs

C. Well-formed versus valid XML

Well-formedValid
Follows the basic XML syntax rules: one root, properly nested and closed tags, quoted attribute values, escaped & and <, case-matched tagsWell-formed and conforms to a DTD or XML Schema (allowed elements, order, data types, ranges)
Checked by every XML parserChecked only by a validating parser against a schema
<stock>150 without a closing tag is not well-formed<category>Toys</category> is well-formed but not valid because Toys is not in the enumeration
A not well-formed file cannot be processed at allA valid file is guaranteed to have the expected structure and values

D. DTD compared with XML Schema

FeatureDTDXML Schema (XSD)
SyntaxSpecial non-XML syntax (<!ELEMENT ...>)Written in XML itself, so ordinary XML tools can read and edit it
Data typesAlmost none (#PCDATA, CDATA, ID)40+ built-in types (xs:decimal, xs:integer, xs:date) and user-defined types
RestrictionsCannot limit a number range, pattern or lengthpattern, enumeration, minInclusive, maxInclusive, length
NamespacesNot supported properlyFully supported
Occurrence controlOnly ?, *, +Exact minOccurs / maxOccurs
Reuse and extensionLimited (entities)Type inheritance (extension, restriction) and reuse
Uniqueness and keysID / IDREF only (whole document)xs:unique, xs:key, xs:keyref scoped to part of a document
Size and learningShort and simpleMore verbose, but much more precise

E. How XML parsers check a document

Parser typeWhat it checks
Non-validatingChecks well-formedness only; it does not compare the file with a DTD/XSD (faster; the default in most libraries)
ValidatingChecks well-formedness and then validity against the DTD or schema, and reports every violation
DOMReads the whole document into a tree in memory; allows random access and changes; uses memory proportional to file size
SAX (push) / pull parser (XMLReader)Reads sequentially and raises events (start element, text, end element) or lets the program pull the next node; small memory, read-only and forward-only, suited to very large files

Both DOM and SAX parsers can be validating or non-validating; validation is a separate option from the parsing style. In PHP, DOMDocument::load() checks well-formedness and schemaValidate() (or schemaValidateSource() for a string) performs validation against an XSD. libxml_use_internal_errors(true) collects the messages so that the program can list them instead of printing warnings.

F. Three kinds of errors reported for a faulty supplier file

Kind of errorParser messageCauseCorrection
1. Pattern violation[facet 'pattern'] value 'PX12' not accepted by P[0-9]{5}Product ID does not have the letter P followed by exactly five digitsSupplier supplies a correct ID such as P10234; if the ID scheme changes, the XSD pattern is updated
2. Enumeration violation[facet 'enumeration'] 'Toys' is not an element of the set {...}Category is not one of the five allowed values (or is spelt differently, e.g. "laptop")Use an allowed value; to sell a new category, add <xs:enumeration> to the XSD after agreeing it with suppliers
3. Range violation[facet 'minInclusive'] -499.00 is less than 1.00; [facet 'maxInclusive'] 25000 is greater than 10000Price is negative; stock exceeds the allowed maximum (typing error)Correct the value to lie within the range (price 1–500000, stock 0–10000)

Other errors are caught in the same way: a missing or out-of-order element (for example warranty omitted) gives "Missing child element(s)", an undeclared element gives "This element is not expected", a missing id gives "The attribute 'id' is required", and a duplicate ID breaks the xs:unique rule. A file that is not well-formed (for example the unclosed <stock> tag or a bare & in products_notwellformed.xml) is rejected earlier, with messages such as "Opening and ending tag mismatch" and "xmlParseEntityRef: no name"; it is corrected by closing the tag and writing &amp;.
