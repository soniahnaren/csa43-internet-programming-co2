Question 2. A college is rebuilding its course-feedback system, currently written in plain PHP with HTML, SQL and validation mixed in the same files, using the Laravel or Symfony framework. Students submit ratings and comments for each course, and the department reviews summary reports. Analyse how the MVC architecture of the framework enhances the application by explaining routing, controllers, models and the ORM (Eloquent or Doctrine), migrations, templates (Blade or Twig), request validation, middleware and CSRF protection. Describe how the database connection is configured (environment file, drivers, credentials) and trace the flow of a request for submitting feedback from the route to the database and back to the view. Discuss the benefits and drawbacks of using a framework compared with plain PHP, and the factors for choosing between Laravel and Symfony.

ANSWER 2 – Course-feedback system rebuilt with Laravel (MVC)

Why MVC helps. In the old plain-PHP files, HTML, SQL and validation are mixed, so one change can break another part, the same query is copied into several pages, and security checks are easy to forget. Laravel separates the application into Model (data and rules), View (presentation) and Controller (request handling), and supplies routing, validation, CSRF protection and database access as tested building blocks.

B. Database connection configuration

Laravel reads connection settings from the `.env` file in the project root. config/database.php uses env('DB_HOST') and similar calls, and DB_CONNECTION chooses the driver (mysql, mariadb, pgsql, sqlite, sqlsrv). Credentials stay out of the code base: .env is listed in .gitignore, each server has its own file, and .env.example documents the keys. In production php artisan config:cache caches the configuration for speed, and the application should use a database account with only the rights it needs. APP_DEBUG must be false in production so that errors do not reveal settings.

D. Request flow: submitting feedback (route -> database -> view)

  1. Browser: the logged-in student opens /feedback/create; FeedbackController@create loads courses with Course::orderBy('code')->get() and returns the Blade view (the form contains a hidden CSRF token).
  2. Submit: the browser sends POST /feedback with _token, course_id, rating and comment.
  3. Front controller: public/index.php boots Laravel and creates the request object.
  4. Middleware: session start, CSRF verification middleware (wrong token -> 419), auth (not logged in -> redirect to login).
  5. Routing: routes/web.php matches POST /feedback and selects FeedbackController@store.
  6. Form Request validation: StoreFeedbackRequest checks the rules. On failure Laravel redirects back with the error messages and old() input; the controller is never called.
  7. Controller: $request->validated() returns only the checked fields; Feedback::updateOrCreate(...) is called.
  8. Model / ORM / database: Eloquent generates a parameterised INSERT (or UPDATE if the student already rated that course, thanks to the unique (user_id, course_id) key) and runs it through the connection from .env.
  9. Response: the controller returns redirect()->route('feedback.create')->with('status', ...) (Post/Redirect/Get, so refreshing does not resubmit the form).
  10. View: the browser follows the redirect with a GET; Blade shows the flash message from session('status').
  11. Reports: department staff open /reports/feedback; the dept middleware allows them; report() runs withCount and withAvg (one SQL query with aggregates) and report.blade.php prints the table.

F. Choosing between Laravel and Symfony

FactorLaravelSymfony
Learning curve and speedGentler; strong conventions and generators give very fast resultsSteeper; more explicit configuration, but very flexible
ORMEloquent (Active Record): simple, fast to writeDoctrine (Data Mapper): entities separate from persistence; better for complex domain models
TemplatesBladeTwig (sandboxed, strict, widely used outside Symfony)
Architecture styleOpinionated "batteries included"Reusable decoupled components (many other projects, including Laravel, use them); suited to large, long-lived systems
EcosystemBreeze/Jetstream, Livewire, queues, scheduler, hosting toolsBundles, API Platform, Messenger; strong in enterprise integration
MaintenanceFrequent releases; upgrades should be planned each yearLong-term-support releases suit organisations that upgrade rarely

Recommendation. For a college feedback system (forms, ratings, summary reports, a small team and a short delivery time) Laravel is the better fit: login via Breeze, Eloquent aggregates for the reports and Blade views can be produced quickly. Symfony would be chosen if the system must join a large enterprise platform, needs a rich domain model with strict layering, or must follow a long upgrade cycle.
