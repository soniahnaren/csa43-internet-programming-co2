ANSWER 2 – Describing and testing the student-result web service

Idea. A SOAP service is described by a WSDL document, a machine-readable contract that tells any client what operations exist, what messages they exchange, which protocol and encoding are used and where the service is located. Because the contract is precise, clients can be generated from it and the service can be tested systematically.

A. Structure of a WSDL document

ElementWhat it describesIn student_result.wsdl
typesThe data types, written in XML Schema (XSD)RegisterNumberType, SemesterType, GradeType, SubjectResultType and the root elements getStudentResult, getStudentResultResponse, ResultFault
messageThe abstract data that is sent or received; each part refers to a type or elementGetStudentResultInput, GetStudentResultOutput, ResultFaultMessage
portTypeThe abstract interface: a set of operations (like a class interface)StudentResultPortType
operationOne callable action with input, output and optional fault messagesgetStudentResult (input, output, fault ResultFault)
bindingHow the interface is carried: protocol (SOAP 1.1), transport (HTTP), style and encoding (document/literal)StudentResultBinding with soap:binding style="document"
serviceA group of ports; the deployed serviceStudentResultService
portOne endpoint: a binding plus a network addressStudentResultPort, soap:address location="http://127.0.0.1:8083/server.php"

The first three (types, message, portType) are the abstract part ("what"); binding, service and port are the concrete part ("how and where"). The address can be changed without touching the interface.

B. Binding styles: document/literal and RPC

AspectDocument/literalRPC (rpc/encoded or rpc/literal)
Body contentThe body holds an XML document that follows a schema elementThe body holds an element named after the operation, containing one child per parameter
Message partspart uses element="..."part uses type="..."
ValidationThe whole body can be validated against the XSDOnly parameters are typed; the wrapper is not in the schema
InteroperabilityRecommended by WS-I (document/literal wrapped is the common form); the style used hererpc/encoded is not WS-I compliant and is rarely used today; rpc/literal is simpler but less flexible
Operation name in the messageNot guaranteed unless "wrapped" (root element named like the operation)Always present
EvolutionEasier: add optional elements to the schemaHarder: changes alter parameters

C. Role of XML Schema in the types section

  • Data contract: every element, its order, its type and how many times it may occur are defined once and shared by all clients.
  • Restrictions: the register number must match the pattern [0-9]{9}, the semester must be between 1 and 8 (minInclusive/maxInclusive) and the grade must come from an enumeration (O, A+, A, B+, B, C, U).
  • Reuse and structure: named simple and complex types (SubjectResultType) are reused; maxOccurs="unbounded" allows any number of subjects.
  • Tooling: stub generators (wsimport, wsdl2java, .NET svcutil) build typed classes from the schema; SoapUI creates sample requests from it; a validating parser can check any message.
  • Caution: a SOAP server does not automatically enforce the schema. In the PHP service the same rules are repeated in code (preg_match, range checks), which is also needed for security.

F. Testing with SoapUI and Postman

SoapUI: File > New SOAP Project > enter the WSDL URL (http://host/server.php?wsdl). SoapUI reads the WSDL and creates a sample request for getStudentResult. Add a TestSuite with one test case per scenario below, and attach assertions: *Not SOAP Fault* (valid case), *SOAP Fault* (error cases), *XPath Match* (for example //ns1:gpa exists), *Schema Compliance* (response matches the WSDL), *Contains* (error code text) and *Response SLA* (for example under 500 ms). A LoadTest with several threads checks response time under load, and the *Security Test* feature adds XML bomb, SQL-injection and oversized-request scans. Postman: create a POST request to the endpoint, set Content-Type: text/xml, SOAPAction and the API-key header, paste the SOAP envelope in the raw body, and write tests in JavaScript (pm.test, pm.response.to.have.status, pm.response.responseTime). Other checks to include: wrong HTTP method and wrong SOAPAction; very long values and a request larger than the limit (rejected before parsing); special characters (<, &) in the register number; repeated calls to check rate limiting; HTTPS only with a valid certificate; confirm the response never contains stack traces; and a load test for the response-time target. These response times were measured on one machine with a built-in server and do not represent production performance.

G. WSDL-first compared with code-first

AspectWSDL-first (contract-first)Code-first
Starting pointDesign the WSDL/XSD, then generate server skeletons and client stubsWrite the classes, then generate the WSDL from annotations or reflection
Interface controlFull control of names, types, namespaces and faults; stable contractContract depends on the framework and can change when code is refactored
InteroperabilityBetter: types are chosen deliberately with other platforms in mindRisk of language-specific types (maps, dates, collections) that other tools handle badly
Team workTeams (university, partner colleges, mobile developers) can agree on the contract first and work in parallelConsumers must wait for the code
Speed and effortSlower start; WSDL/XSD must be written by hand or with a toolFast prototyping; little XML knowledge needed
MaintenanceChanges start in the contract, so versions are explicitEasy to break clients by accident
Best forPublic or inter-organisation services that must last (results, billing)Internal services and quick prototypes

Recommendation. For a university result service that colleges, mobile apps and other systems will rely on, use WSDL-first: design the contract (with the restrictions shown above), review it with the consumers, generate the skeleton, and keep the schema checks in code as a second layer of defence. Code-first is acceptable for an internal prototype.
