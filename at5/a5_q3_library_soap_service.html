Question 3. A college library keeps its book records in a relational database and wants to offer them to other applications as a database-driven SOAP web service. Develop the solution by explaining how the service is created (for example, JAX-WS in Java or SoapServer in PHP) with operations such as searchBook, getBookDetails and issueBook; how the operations access the database using JDBC or PDO with prepared statements and transactions; how SOAP faults report errors; and how the WSDL is published. Then explain how a client application consumes the service, by generating client stubs from the WSDL or using SoapClient, building the request, calling the operation and processing the response. Evaluate how the design handles SQL injection, concurrent issue requests, authentication and error handling, and discuss when a REST service would be preferred to SOAP.
Marks (10)   (CO5)   (BL5)

ANSWER 3 – Database-driven SOAP web service for the college library

Idea. The library keeps its book records in a relational database. A SOAP service publishes three operations so that other applications can use the records without direct database access: searchBook, getBookDetails and issueBook. The database stays private behind the service; clients see only the WSDL contract.

OperationInputOutputAccess
searchBookkeyword (2–60 characters)list of books: id, title, author, ISBN, availablePublic and desk keys (read)
getBookDetailsbookIdtitle, author, ISBN, total and available copiesPublic and desk keys (read)
issueBookbookId, memberIdloanId and due date (14 days)Desk key only (write)

A. How the service is created and the WSDL published

PHP: SoapServer is created from the WSDL and an object whose public methods implement the operations (setObject). handle() reads the SOAP request, calls the matching method and writes the response; a thrown SoapFault becomes a Fault message. The WSDL is published by serving the file when the URL ends with ?wsdl, so clients can fetch the contract from the endpoint. Java (JAX-WS): annotate a class with @WebService, and Endpoint.publish() starts the endpoint and publishes the WSDL automatically at ?wsdl.

B. Database access with prepared statements and transactions

Every query uses a prepared statement (PDO in PHP, PreparedStatement in JDBC): the SQL text is fixed and the values are bound as parameters, so user input can never change the structure of the query. issueBook changes three things (member check, stock, loan record) and must succeed or fail as a whole, so it runs in one transaction: BEGIN ... COMMIT, with ROLLBACK on any error. The stock is reduced with a single conditional statement, UPDATE books SET available_copies = available_copies - 1 WHERE id = :b AND available_copies > 0, and the service checks that exactly one row was changed. The database applies this check and change atomically, so two requests can never take the last copy. In MySQL (InnoDB) the member row is also locked with SELECT ... FOR UPDATE so that two requests for the same member are processed one after the other and the three-book limit cannot be bypassed; SQLite (used for the offline demo) takes the write lock with BEGIN IMMEDIATE.

C. Reporting errors with SOAP faults

A SOAP Fault carries a faultcode (Client means the request was wrong, Server means the service failed), a human-readable faultstring and optional detail. The service uses Client faults with a stable error code at the start of the text, so a client program can decide what to do without parsing prose. Unexpected errors are logged on the server and the client only receives a generic ERR_INTERNAL fault, so table names or SQL never leak.

D. How a client consumes the service

  1. Obtain the WSDL from http://host/server.php?wsdl.
  2. Create the client: in PHP new SoapClient($wsdl, [...]) (the WSDL lets it expose each operation as a method); in Java run wsimport -keep -p library.client http://host/library?wsdl to generate stub classes and use the generated LibraryService port.
  3. Build the request: pass an array/object whose fields match the schema (for example ['keyword' => 'program']); the client turns it into the SOAP envelope and adds the API-key header.
  4. Call the operation like a normal method; the client sends the HTTP POST.
  5. Process the response: the XML reply is converted back to objects ($found->book). A single result arrives as one object, not a list, so the code wraps it into an array.
  6. Handle faults: wrap calls in try/catch (SoapFault) and act on the error code.

F. When a REST service would be preferred to SOAP

Choose REST whenChoose SOAP when
Clients are web or mobile apps and browsers (JSON, lightweight)Clients are enterprise or legacy systems that expect a WSDL contract and generated stubs
Mostly simple CRUD on resources (books, members, loans) such as GET /books?q=..., POST /loansA strict contract, standard faults and formal typing are required
Responses should be cached (catalogue search) and bandwidth mattersWS-Security (message-level signing/encryption), WS-ReliableMessaging or WS-AtomicTransaction are needed
Many third-party developers need an easy APIOperations are action-oriented and the partner already uses SOAP tooling

Verdict. For a library catalogue that students' mobile apps and the college website will use, REST is the better public interface. The SOAP service is appropriate where partner systems (for example another library network or the university ERP) already consume WSDL. The design shown keeps the important protections (prepared statements, atomic stock update, role-based keys, safe faults) independent of the protocol, so the same core could later be exposed through REST as well.
