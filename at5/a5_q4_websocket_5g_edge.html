Question 4. A city ambulance service wants a web application that shows live ambulance locations on a map and streams vital signs of patients from the ambulance to the hospital emergency team, with delays of only a few milliseconds. Analyse how WebSockets, 5G and edge computing support this requirement. Explain the WebSocket handshake (HTTP Upgrade), full-duplex communication, message events and heartbeat handling, and compare WebSockets with polling, long polling and Server-Sent Events. Explain the 5G features that matter for web applications (eMBB, URLLC, mMTC, network slicing) and the role of edge computing and multi-access edge computing (MEC) in processing data near the ambulance. Discuss the issues of reconnection, scaling of connections, security (WSS, authentication and origin checks) and data privacy, and justify your choice of where to place each component.

ANSWER 4 – Live ambulance tracking and vitals streaming (WebSockets, 5G, edge)

Requirement. Ambulance positions must move on a map and patient vital signs must reach the emergency team within a few milliseconds. Ordinary request/response web pages cannot do this: the browser would have to keep asking. The design combines three technologies: WebSockets (a permanent two-way connection that lets the server push data the moment it arrives), 5G (a radio network that can give low latency and high reliability to moving vehicles) and edge computing (processing close to the ambulance instead of in a distant data centre).

B. The WebSocket protocol

Handshake (HTTP Upgrade). A WebSocket starts as an ordinary HTTP/1.1 GET request that asks the server to switch protocol. The client sends a random Sec-WebSocket-Key; the server proves it understood by returning Sec-WebSocket-Accept (the key combined with a fixed GUID, hashed with SHA-1 and Base64 encoded) and status 101 Switching Protocols. After that the same TCP connection carries WebSocket frames instead of HTTP. Because the handshake is an HTTP request, the server can check the Origin header and the credentials before it accepts the connection.

  • Full-duplex: both sides can send at any time on the same connection; the ambulance sends data while the hospital sends commands (subscribe, resume) without opening new connections.
  • Framing and overhead: after the handshake each message has only a 2–14 byte frame header (HTTP requests carry hundreds of bytes of headers every time), which is why latency and bandwidth are low.
  • Events (browser API): onopen (connected), onmessage (data arrived), onerror and onclose (with a close code such as 1000 normal, 1008 policy violation, 1009 message too big).
  • Heartbeat: a connection can become half-open (phone enters a tunnel and no close is ever sent). The server sends a protocol ping every interval; the client answers with pong; no pong for one interval means the socket is terminated. Browsers cannot see protocol pings, so the server also sends an application message hb, and the page closes and reconnects if nothing arrives for three intervals.

Conclusion. The ambulance must send data and the hospital must receive and also send control messages (subscribe, resume), so WebSocket is the best fit. SSE would be a reasonable choice if the dashboard only needed to receive and proxies blocked WebSockets; polling and long polling are fallbacks for restricted networks.

These are standard design targets; what a particular operator delivers depends on spectrum, coverage, the core network and agreements. The system must therefore also work, with higher delay, on 4G or Wi-Fi.

E. Role of edge computing and multi-access edge computing (MEC)

Edge computing runs software near where data is produced instead of in a distant cloud. MEC is the telecom-standard form: compute and storage are placed inside or next to the mobile operator's radio and core network, so traffic from the ambulance can be processed without leaving the local network.

  • Latency: fewer network hops; critical-alert rules and the WebSocket gateway run within the city.
  • Bandwidth and cost: the edge filters and summarises raw readings (for example one alert instead of 100 identical values) before sending to the cloud.
  • Resilience: the edge keeps relaying data and alerts if the link to the central cloud is slow or down.
  • Privacy and compliance: patient data can stay in the region and only the necessary data is stored centrally.
  • Drawbacks: many small sites to operate and secure, less capacity than the cloud, and the need to synchronise state with the cloud.

G. Test results

The measured relay time of about 1.5 ms (median) is the cost of the server code alone on localhost. It does not include radio, core network or distance, so it shows that the software adds very little to the budget above, not that the end-to-end target is met. The dashboard page was served and its code reviewed but it was not opened in a real browser, and WSS was not exercised during these tests.

H. Justification of the choices

WebSocket over WSS carries both directions with the lowest overhead and is supported by browsers. 5G with a URLLC/emergency slice gives the moving ambulance prioritised, low-delay access that public networks cannot guarantee. MEC hosts the gateway and alert rules near the ambulance for the delay budget, while cloud or hospital data centres hold the durable, regulated data. The weak points are operator dependence (coverage, slice availability) and operating many edge sites; both are reduced by a fallback to 4G/Wi-Fi, automatic reconnection with replay, and local alarms in the ambulance that do not depend on the network.
