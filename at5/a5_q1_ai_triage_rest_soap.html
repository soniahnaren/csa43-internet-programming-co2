Question 1. A multi-speciality hospital plans to add an AI-powered patient-support service to its web portal. The service must classify the urgency of a patient's symptom message (low, medium or high) using a trained AI model, return a suggested department, and be usable by the hospital's mobile app (through a REST API) and by the legacy billing and appointment systems of partner clinics (through a SOAP API). Design the integration by explaining the architecture in which the AI model is deployed behind a web service; the REST design (resources, URIs, HTTP methods, JSON request and response, status codes, statelessness); the SOAP design (envelope, header, body, fault); and authentication and authorisation (API keys, OAuth 2.0 tokens, WS-Security). Compare REST and SOAP for this case, and analyse the issues of latency, rate limiting, input validation, privacy of patient data, model errors or bias, and API versioning, with the measures you would take for each.

ANSWER 1 – AI-powered patient triage behind REST and SOAP web services

Idea. The trained model is not called directly by any client. It is deployed behind a web service that checks identity, validates input, applies safety rules, records an audit trail and only then asks the model for a prediction. The same core logic is offered through two interfaces: REST/JSON for the mobile app and SOAP/XML for the legacy systems of partner clinics, so both receive identical answers.

A. Architecture: the AI model deployed behind a web service

ComponentRoleWhy it is separate
API gateway / reverse proxyTLS termination, authentication, rate limiting, request-size limits, loggingOne place to enforce security for both REST and SOAP
Triage service (PHP in the demo)Two thin adapters (REST and SOAP) over one core: validate -> classify -> safety rules -> storeBusiness rules are written once; interfaces can change without touching the model
Model serverHosts the trained classifier (for example ONNX Runtime, TensorFlow Serving or a Python service) and returns urgency, department and confidenceScales independently (GPU nodes), can be upgraded or rolled back without changing clients, is never exposed to the internet
DatabaseStores request id, pseudonymous patient reference, result, model version, timeAudit and quality review; the symptom text itself is not stored (data minimisation)
MonitoringLatency, error rate, confidence distribution, urgency mix per model versionDetects model drift and outages early

In the code, classifier.php defines a Classifier interface with two implementations: KeywordClassifier (a stand-in model so the service runs offline) and HttpModelClient (calls the real model server with a 2-second timeout). apply_safety_rules() wraps any model.

B. REST design

Method and URIPurposeSuccessNotes
POST /v1/triage-requestsSubmit a symptom message; creates a triage request resource201 Created + Location headerNot idempotent; body is JSON
GET /v1/triage-requests/{id}Read an earlier result200 OKA client can read only its own requests
GET /v1/healthLiveness check for the load balancer200 OKNo authentication, no data

Resources are nouns (triage-requests), the HTTP method gives the action, and the version is in the URI (/v1). Statelessness: every request carries its own credentials (X-API-Key or Authorization: Bearer ...) and everything the server needs; no session is kept between calls, so any server instance can answer and the service scales horizontally behind a load balancer.

C. SOAP design

A SOAP message is an XML Envelope that contains an optional Header (metadata such as security tokens) and a mandatory Body (the operation and its data). Errors are returned as a Fault element (faultcode, faultstring, optional detail). The contract is the WSDL (triage.wsdl, document/literal): operation classifyUrgency with an input message, an output message and a fault.

D. Authentication and authorisation

MechanismHow it worksUsed forStrengths / limits
API keySecret string sent in X-API-Key; the server stores only its SHA-256 hash and compares in constant timePartner clinic back-end serversSimple. Identifies an application, not a person; must be rotated; never put in a mobile app
OAuth 2.0 bearer tokenAn authorisation server issues a short-lived signed token (JWT) with sub, iss, exp and scope; the API checks signature, issuer, expiry and scopeMobile app and web portal (user or client-credentials flow)Short life, scopes give least privilege, revocable, no password reaches the API
WS-Security UsernameToken (digest)Header carries username, nonce, timestamp and Base64(SHA1(nonce + created + password)); server recomputes, checks age (5 min) and rejects reused noncesSOAP partner systemsStandard for SOAP; password never sent; replay-protected. Message signing/encryption (XML-DSig, XML-Enc) or mutual TLS can be added for stronger protection

Authorisation answers "what may this caller do?". Tokens carry scopes (triage:write to create, triage:read to read) and the code returns 403 when a scope is missing. Data access is also restricted by owner: a client can read only the requests it created. Transport is always TLS (HTTPS).

E. REST compared with SOAP for this case

CriterionREST (JSON over HTTP)SOAP (XML with WSDL)
Format and sizeCompact JSON; light for mobile networksVerbose XML envelope; larger and slower to parse
ContractOpenAPI description (optional, by convention)WSDL + XSD is mandatory and strict; stubs are generated automatically
SecurityTLS + OAuth 2.0 / API keysTLS + WS-Security (signing, encryption, tokens) built into the standard
Standard error handlingHTTP status codes and JSON error bodyStandard Fault element
Caching and toolingUses HTTP caching and simple tools (curl, browsers)Requires SOAP-aware tools; POST only, so not cacheable
Fit with legacy billing and appointment systemsPoor: many older enterprise systems cannot call JSON APIsGood: these systems already consume WSDL contracts
Fit with the mobile appExcellentPoor (heavy libraries, battery and data cost)

Conclusion. Use REST as the primary interface for the mobile app and offer SOAP as an adapter for partner clinics. Because both call the same run_triage() core, the answers, the safety rules and the audit trail are identical.

F. Issues and the measures taken

IssueRiskMeasures
LatencyA slow model delays triage; patients may wait or abandon the serviceLatency budget (for example 2 s for the model call, enforced with CURLOPT_TIMEOUT_MS); model server close to the API; keep models small or quantised; asynchronous processing for heavy models; connection reuse; monitor p95. If the model times out the service fails safe: it returns "medium" with human review, never a silent "low"
Rate limitingAbuse, scraping, accidental loops and denial of serviceToken bucket per client (5 burst, 1 per second in the demo) returning 429 with Retry-After and X-RateLimit-* headers; request-size limit of 8 KB; limits also at the gateway/WAF; larger quotas for trusted partners
Input validationInjection, huge or malformed input, unexpected typesServer-side checks: message 5–1000 characters with control characters removed, patient_ref must match [A-Za-z0-9_-]{6,40}, language from a whitelist, JSON depth limit, Content-Type check; prepared SQL statements; XML: DTDs not accepted
Privacy of patient dataSymptoms are sensitive health dataTLS everywhere; pseudonymous `patient_ref` only (no name, phone or address accepted); the message text is not stored; Cache-Control: no-store; no personal data in URLs or logs; access limited by scope and by owner; encryption at rest; retention rules; consent notice and compliance with data-protection law (for example India's DPDP Act 2023, and GDPR/HIPAA where they apply)
Model errors and biasA missed emergency (false negative), different accuracy for some languages, ages, genders or dialects, over-reliance on the outputTune for high sensitivity on "high" urgency; confidence below 0.60 is escalated one level; every "high" result needs human review; clear disclaimer; test accuracy per subgroup before release; log model version with each result; monitor drift and compare outcomes; clinical governance review; allow staff to override and feed corrections back to retraining
API versioningChanges break existing clients, especially fixed legacy systemsVersion in the URI (/v1); only add optional fields within a version; announce deprecations with a Sunset header; run /v1 and /v2 side by side; SOAP uses a versioned namespace and keeps old WSDLs; model_version is returned so results are traceable

G. Test results

Verdict. The design is justified: the model sits safely behind one controlled service, each client type gets an interface it can actually use, and the main risks (latency, abuse, invalid input, privacy, wrong predictions and breaking changes) each have a concrete control. The remaining risk is clinical: the service must remain decision support with human review for urgent cases, and the model needs continuous monitoring after release.
